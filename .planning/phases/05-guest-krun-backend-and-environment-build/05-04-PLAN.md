<objective>
Define the guest's wire contract in `minos-core`: the guest job (v1 JSON), the guest status file (`.minos/status.json`), and the input disk v2 layout with its per-launch token, each with one codec shared by host and guest.

Purpose: GUEST-02 has the guest read the job (base tarball, canonical diff, manifest subset) from a read-only input disk; D-15 has the backend write that disk from blob bytes and never store it as a blob; GUEST-04's authenticated output needs the token delivered on that disk only. D-07 keeps the decoders byte-oriented so a later lifecycle-hook source reuses them.
Output: `guest.rs`, golden snapshots, codec tests, and a snapshot-cap test in minos-source.
</objective>

<threat_model>
## Trust Boundaries

| Boundary | Description |
|----------|-------------|
| host -> guest input disk | The backend writes the disk; the guest validates it as if hostile |
| guest -> host status | PID 1's status file returns inside the authenticated stream, but a kernel-exploited guest could forge it, so it is parsed as hostile |

## STRIDE Threat Register

| Threat ID | Category | Component | Severity | Disposition | Mitigation Plan |
|-----------|----------|-----------|----------|-------------|-----------------|
| T-05-04-01 | Tampering | Input disk sections | high | mitigate | Per-section SHA-256 in the table, checked after reading; BASE bound to the job's TreeId and DIFF to its BlobId by check_role |
| T-05-04-02 | Denial of service | Oversized or malformed disk tables | medium | mitigate | Header and table validated (caps, order, alignment, overlap) before any section byte is read |
| T-05-04-03 | Spoofing | Token delivery | high | mitigate | The token travels only in the disk header (never in the job JSON or any blob); 05-12 removes /dev/vdb after PID 1 reads it |
| T-05-04-04 | Information disclosure | Free text in the status | medium | mitigate | GuestStatus holds enums, numbers, and RelPaths only; parsed under a byte cap with deny_unknown_fields |
| T-05-04-05 | Elevation of privilege | A job that runs stages the role should not | medium | mitigate | Stage lists fixed per role in try_from; a judge job carries no base, diff, or writable set |
</threat_model>
