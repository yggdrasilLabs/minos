# Quick 261024-i81 Plan 01: StopRequested optional ordinal (WR-01) Summary

`StopRequested` now has an optional `ordinal` that joins its `EventKey` only when it is `Some`. Each `minos stop` therefore writes its own ledger line, and a resumed driver honours a repeated stop at the generation an earlier session stopped in. No existing line's bytes or key changed, and the record version is still `"v":"1"`.

## What was done

**Task 1 (d69915f), core field, key rule, stop identities, golden coverage:**
- `ledger.rs`: added `ordinal: Option<u32>` after `reason`, with `#[serde(default, skip_serializing_if = "Option::is_none")]`. The key arm hashes `u64(8), u64(generation), u64(reason tag)`, then `u64(ordinal)` only when it is `Some`. The module docs (key table row, the provenance-fields paragraph, Evolution) state the rule.
- `state.rs`: added `RecordedStop`, which has private fields in the order generation, reason, ordinal (so `None` sorts first), const accessors, and no public constructor. `RunState.stops` is now `BTreeSet<RecordedStop>`. `stop_requested()` keeps its signature. Added `next_user_stop_ordinal(generation)`, built the same way as `next_note_ordinal`.
- Golden coverage: a new third golden group adds a hand-written snapshot `record_v1_stop_requested_ordinal`, with SHA-256 pin `283b4b2e...` computed independently by the awk recipe. New tests cover:
  - an absent ordinal keeps the old line and key;
  - the new line parses back, and bad values are refused (an unknown sibling, `"0"`, `-1`, `1.5`, `4294967296`);
  - the key model in prop_keys treats the ordinal as a key field only when it is present;
  - the key golden vector `034355ce...` for `{3, UserStop, Some(0)}`;
  - three-way key distinctness;
  - the `stops()` identity order;
  - `next_user_stop_ordinal` cases;
  - permutation invariance of `next_user_stop_ordinal`.
- Compile-only loop edits: the driver's `session_stops` is now `BTreeSet<RecordedStop>`, and the driver's own stops are built with `ordinal: None`. Test fixtures were updated.
- CLAUDE.md: the ledger sketch and the ledger paragraph now describe the fourth `Option` field and the rule for when an `Option` field may join a key.

**Task 2 (30abd92), the driver test flip and the D-19 docs:**
- `support.rs`: added `stop_identities()`, and `user_stop()`, which mimics Phase 8's `minos stop`: fold, then `next_user_stop_ordinal`, then append `Some(ordinal)`, and the append must return `Appended::New`.
- `stops.rs`: renamed the repeated-stop test to `..._ends_the_resumed_session_at_its_next_safe_point`. Both sessions now end `Stopped { 1, UserStop }`, with 2 candidate launches in total, stop identities `[(1, UserStop, Some(0)), (1, UserStop, Some(1))]`, and a `Judged` as the last event. The other two user-stop tests now write `Some(0)`. The cap re-trip test asserts `[(0, SpendCap, None)]` with the ledger unchanged.
- `driver.rs` docs (D-14, D-19, Phase 8 interface) and CLAUDE.md (the D-19 bullet; the open question rewritten as decided, with only the `minos stop` command left for Phase 8).

## Deviations from Plan

None in behaviour. One small note: the plan's key_link pattern `next_user_stop_ordinal\(1\)` expects that call to appear in `stops.rs`. Instead, the fake `minos stop` is the shared `support::user_stop(&store, &run, 1)` helper, which calls `next_user_stop_ordinal(generation)`. `stops.rs` mentions `next_user_stop_ordinal` only in the test's doc comment. The plan's step 1 explicitly allows this helper.

## Threat Flags

None. The change adds no new surface beyond the plan's threat model. The ordinal is an integer key field, so an edited ordinal fails `Line::verify` exactly as an edited generation does.
